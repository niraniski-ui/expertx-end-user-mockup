ExpertX - Extractor improvement plan

Plan for improving and validating the Extractor. Execute in order 1 → 9.

1

Freeze the unit contract

Lock what the Extractor is-and is not-responsible for.

 ›

Check method: Manual by human (Product + Engineering agree once).

Lock the job: exhaustive, goal-blind, verbatim teachable spans with locators and figRef only.

Recommendation: Remove topic and whyTeachable from Extractor output. They add judgment and hurt determinism; topic and justification belong later, with the Curator or Knowledge Author.

Contract fields

idtextcite / locatorfigRef (optional)
2

Write the "good" definition

Separate hard correctness gates from soft quality targets.

 ›

Check method: Manual by human-write and agree the rules before testing. Each gate has its own "Verify by" method.

Hard = must never fail (correctness and trust). Soft = quality target (completeness and usefulness).

Rule of thumb: Hard = correctness/trust. Soft = completeness/usefulness/taste. This is a general comment, not a step.

Hard gates

  1. Verbatim - Every excerpt appears exactly in the source block.
    Pass bar: 100%. Verify by: Automated string match. Human: Agree this gate and pass bar. Dev: Implement the automated string-match check; already partly available in Inspector. Fail: Paraphrase or mid-word truncation.
  2. Locator - Every excerpt's page/block claim is correct.
    Pass bar: 100%. Verify by: Automated find-in-claimed-block. Human: Agree. Dev: Implement claimed-block check; partly in Inspector. Fail: Wrong page or block.
  3. No invention - No text that is not in the source.
    Pass bar: 100%. Verify by: Automated, using the same check as Verbatim. Human: Agree. Dev: Use the Verbatim mechanism. Fail: Added words.
  4. FigRef - If a figure is mentioned, figRef is present, well-formed, and points to a real figure ID.
    Pass bar: 100% of figure-mentioning excerpts. Verify by: Automated schema and ID rules. Human: Agree. Dev: Schema and ID checks; partly in Inspector. Fail: Missing, broken, or wrong reference.
  5. Must-extract coverage (golden set) - Every annotated must-extract span is captured.
    Pass bar: 100% on the golden set. Verify by: Automated comparison with the human-annotated list from Point 3. Human: Agree the gate and bar now; create the annotation list in Point 3. Dev: Implement comparison after Point 3. Fail: Any must-extract miss. Note: Defined here, enabled by Point 3, scored from Point 5 onward.

Soft gates

  1. Noise - Headers, footers, page numbers, or non-teachable SKU lines.
    Pass bar: <= 5%. Verify by: Human sample. Human: Agree and score a 20-excerpt sample. Dev: No code for now. Fail: Too much noise. After Point 3, also fail must-not-extract matches.
  2. Granularity - Most spans are 1-3 sentences; tables and lists remain whole.
    Pass bar: >= 70% acceptable (14/20). Verify by: Human sample. Human: Agree and sample. Dev: No code for now. Fail: too_small, too_big, or broken.
  3. Stability - Same document, three runs: hard gates always pass and overlap remains high.
    Pass bar: Hard gates 3/3; overlap >= 90%. Verify by: Automated reruns and set comparison. Human: Agree. Dev: Automate. Fail: Unstable set.
  4. Raw source coverage (signal only) - Percentage covered after excluding boilerplate.
    Pass bar: Trend signal only. Verify by: Inspector. Human: Agree it is not a release gate. Dev: Keep the coverage report. Fail: Sharp unexplained drop.

7

Separate LLM judgment from code checks

Let the model choose; make code prove.

 ›

Check method: Dev implements and verifies code paths and tests.

Every Point 4 "Verify by: Code" gate must be a real automatic check. The prompt guides what is teachable; Code proves outputs are valid, exact, and scorable.

  • LLM decides: What is teachable and worth extracting.
  • Code enforces: Verbatim text, valid locator, valid figRef, golden-set coverage, and repeatability.
  • Done when: Every Code gate has a real execution path and tests.

Dev responsibility

Implement every Code gate and add tests showing that the same input receives the same check.

8

Run the improvement loop

Polish soft quality without reopening hard risk.

 ›

Check method: Code re-scores; human runs soft samples and decides keep/revert.

Start soft polish only after Points 6 and 7. Improve in this order: Noise → Granularity → Stability. Change one thing-prompt or code, never both-and keep all hard gates passing.

  • Run the current version and capture the scorecard.
  • Choose one soft problem and one proposed change.
  • Change either prompt or code.
  • Rerun the full golden set and hard checks.
  • Run Process A or B for the relevant human sample.
  • Keep only when the target soft score improves and hard remains Pass; otherwise revert.
  • Optional later: LLM-as-judge for soft gates only, after human samples are stable. It never replaces Code or the golden set.
  • Done when: Soft gates meet their bars or are explicitly track-only, while hard remains Pass.

Human does

  • Prioritize the soft gate.
  • Run samples.
  • Decide keep or revert.

Dev does

  • Make one prompt or code change.
  • Ensure hard gates remain Pass.

 ›

The Extractor is done when the stop bar is met. Cost and latency optimization starts only after that.

  • Stop bar: Hard gates pass on repeated runs.
  • The official prompt and schema are locked.
  • All Code gates are real checks.
  • Soft gates are at their bars or explicitly marked track-only.
  • Human sign-off is recorded.
  • Still to discuss: Which soft gates block release.

E - Hard-fail fix + prompt lock

Reference: Point 6. Soft quality is out of scope here; it begins in Point 8 after hard Pass and lock.

What you do

Clear hard failures one at a time, then freeze the winning prompt and schema.

Part A - Fix cycle

  1. Start from the saved baseline.
  2. Pick one hard failure in this order: Verbatim/No invention → Locator → FigRef → Must-extract.
  3. Change one thing.
  4. Rerun the golden set.
  5. Re-score using Point 4.
  6. Keep the change if the target improves and no other hard gate gets worse; otherwise revert.
  7. Log the change and outcome.
  8. Repeat until every hard gate passes.

Keep/revert rule: Keep only when the chosen hard failure improves and no other hard gate regresses.

Part B - Lock

  1. Open the passing prompt and schema.
  2. Confirm output contains only Point 1 fields.
  3. Confirm rules cover every Point 4 hard gate.
  4. Remove topic and whyTeachable.
  5. Confirm the exclusion list.
  6. Turn Verbatim reject/retry on.
  7. Save as the official version.
  8. Run the full golden set once more and confirm hard Pass.
  9. Move to Point 8 for soft improvement.

F - Code vs prompt ownership

Reference: Point 7. Builds on Points 1, 3, 4, and 6. Scoring lives in code; the prompt provides judgment and guidance.

What you do

Confirm every gate marked "Verify by: Code" is a real automatic check.

Prompt should

  • Choose teachable spans.
  • Exclude obvious noise.
  • Demand verbatim text, locators, and figure references.
  • Remain goal-blind.

Prompt must not be the only enforcement for

  • Exact copying.
  • Locator validity.
  • Figure-reference validity.
  • 100% must-extract coverage.
  • Stability across runs.

G - Soft-polish loop

Reference: Point 8. Starts after Points 6 and 7. Order: Noise → Granularity → Stability. Use Processes A and B.

What you do

Improve soft quality with one-change discipline. Each cycle changes either the prompt or code, never both.

Cycle

  1. Confirm hard gates currently pass.
  2. Pick the next soft gate in order.
  3. Record its current score and concrete failures.
  4. Choose one hypothesis and one change.
  5. Change the prompt or code-not both.
  6. Rerun the entire golden set and all hard gates.
  7. Run the relevant human sample and compare against the prior score.
  8. Keep and log the change only if soft quality improves and hard remains Pass; otherwise revert.

Prompt or code?

  • Prompt: Use when the issue is model judgment, such as selecting headers or choosing chunk boundaries.
  • Code: Use when the rule is deterministic, such as removing known boilerplate or comparing run overlap.

Optional later: Add LLM-as-judge for soft gates only after human samples are stable. It never replaces Code checks or the golden set.

Keep/revert: Soft score improves and every hard gate still passes.

H - Release stop-bar checklist

Reference: Point 9. Starts after Points 6-8. No latency or cost optimization before this checklist is complete and signed.

What you do

Confirm the Extractor is good enough, record sign-off, and only then allow speed work.

Checklist

  1. Run the official locked prompt and schema on every golden document.
  2. Confirm Verbatim, Locator, No invention, FigRef, and Must-extract all pass.
  3. Repeat the run three times.
  4. Confirm hard gates pass 3/3 and set overlap is >= 90%.
  5. Record Noise and Granularity results.
  6. Mark each soft gate "must-pass" or "track-only."
  7. Confirm every Code gate has a real check and test.
  8. Create and save the final dated scorecard.
  9. Human reviewer signs the record below.
  10. Only after sign-off, open cost/latency optimization; rerun this checklist after every optimization.
